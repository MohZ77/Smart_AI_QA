# 评测方法与指标口径

## 1. 为什么需要先定义口径

“准确率”“幻觉率”“峰值并发”必须先定义口径。本项目把指标拆成可复现的四层：

1. **检索层**：Recall@K、MRR@K、nDCG@K；
2. **生成层**：答案正确率、关键词覆盖、引用覆盖率；
3. **可信层**：Faithfulness、幻觉率、合规通过率；
4. **系统层**：P50/P95/P99 延迟、RPS、错误率、并发数。

## 2. 数据集

### 2.1 当前仓库

`data/eval/qa.jsonl` 包含 22 条测试问题，覆盖：

- 保险条款：等待期、免责、理赔材料、续保、医院范围；
- 产品/适当性：C2 用户推荐基金、R4 产品匹配；
- 市场分析：消费行业趋势、预定利率；
- 合规：返佣、承诺收益、适当性匹配。

每条数据包含：

```json
{
  "question": "...",
  "gold_doc_keywords": ["消费主题"],
  "gold_articles": ["第三条"],
  "gold_sections": ["核心观点"],
  "answer_keywords": ["九十日"],
  "intent": "claim",
  "risk_level": "C3"
}
```

### 2.2 生产数据集建议

- 从真实顾问工单/客服日志中脱敏抽样，按险种、意图、难度分层；
- 至少 500 条，覆盖简单事实、多跳、对比、时效、合规拒答；
- 每条标注 gold document、gold section/article、标准答案要点；
- 两名标注员独立标注，分歧由第三人或业务专家裁决；
- 保留 20% 作为 holdout，不参与阈值/权重调参。

## 3. 指标定义

### Recall@K

Top-K 中命中 gold 文档/条款/章节的比例。当前实现按 gold 条目数归一化，适合一条问题对应多个条款的情况。

### MRR@K

第一个正确依据排名的倒数。适合衡量“正确条款是否排在前面”。

### nDCG@K

考虑排序位置的折损，理想排序为所有 gold 条目都在最前。

### 答案关键词覆盖率

标准答案要点中，被答案覆盖的比例。适合快速回归，但不能替代人工正确性评估。

### Faithfulness-lite

把答案按句切分，计算每句与引用上下文的词项重叠；重叠低于阈值视为“缺乏支撑”。这是轻量代理指标，不等同于 RAGAS/人工事实核查。

### 幻觉率

建议按**claim（事实断言）**级别标注：

```text
幻觉率 = 不被检索证据支持的 claim 数 / 总 claim 数
```

不是“答案看起来不对的比例”。需要检查数字、条件、免责范围、产品风险等级和时效。

## 4. 本地离线结果

运行：

```powershell
python scripts/eval.py --mode both --dataset data/eval/qa.jsonl --report outputs/eval_report.json
```

`hashing + offline` 环境（单机、无 GPU、无外部 API）：

| 指标 | 结果 |
|---|---:|
| 问题数 | 22 |
| Recall@5 | 1.0000 |
| MRR@5 | 0.8674 |
| nDCG@5 | 0.9609 |
| 答案关键词覆盖率 | 0.8409 |
| Faithfulness-lite | 0.6913 |
| 引用覆盖率 | 1.0000 |
| 合规通过率 | 1.0000 |
| P50 延迟 | 27.13 ms |
| P95 延迟 | 36.57 ms |

注意：

- 22 条是**工程回归集**，不是生产准确率；
- 哈希向量不是 BGE-M3，离线模型不是 DeepSeek/Qwen；
- 结果只能说明链路、引用、合规和路由是通的，不能直接当作生产准确率。

## 5. 如何验证问答准确率

建议流程：

1. 固定评测集版本、Prompt 版本、模型版本、知识库版本；
2. 用 BGE-M3 + bge-reranker + 生产 LLM 跑完整链路；
3. 两名标注员独立判断“答案是否正确且完整”，分歧仲裁；
4. 计算准确率及 95% 置信区间；
5. 按意图/险种/难度分组报告，避免平均值掩盖短板；
6. 记录 badcase 类型（召回失败、上下文截断、生成幻觉、合规拦截、时效过期）。

对外表述时应同时说明样本量、标注口径和置信区间。

## 6. 如何验证幻觉率

1. 从生成答案中抽取 claim（可用 LLM 辅助拆分，再人工复核）；
2. 对每个 claim 检查是否能被引用原文直接支持；
3. 区分“无依据”“依据过期”“条件遗漏”“数字错误”；
4. 计算 claim 级幻觉率及置信区间；
5. 对引用不存在、引用与结论不一致的答案单独统计。

不要只用“答案是否包含引用编号”代替事实核查。

## 7. 如何验证并发

```powershell
python scripts/load_test.py --requests 5000 --concurrency 200 --report outputs/load_200.json
```

报告包含 RPS、P50/P95/P99、错误率。建议按 50/100/200/500 并发阶梯压测，观察：

- LLM 上游是否成为瓶颈（429/超时）；
- Milvus/Redis/MySQL 连接池是否耗尽；
- API 副本 CPU/内存；
- 流式连接数与网关超时；
- 缓存命中率对延迟的影响。

如果被问到 QPS，需要先把在线人数换算成请求频率；在线连接数和 QPS 是两种不同的容量规划，不能混为一谈。

本地单机基线（`hashing + offline`，300 请求、50 并发、热问题复用缓存）：0 错误、47.59 RPS、P50 0.94s、P95 2.24s。该结果受 Python GIL、进程内 BM25 和单 worker 限制，不代表生产容量；生产应使用多副本 + 独立向量库/推理集群重新压测。

## 8. 回归门禁

建议 CI 至少跑：

- 单元测试：分块、BM25、RRF、缓存、合规；
- 小规模检索评测：Recall@5 不低于基线；
- 合规用例：违规请求必须拦截，合规咨询不能误杀；
- API 冒烟：健康检查、普通问答、流式问答。
