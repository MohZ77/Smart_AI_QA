# 容灾、降级与数据增长

## 1. 先明确容量口径

下面是容量规划假设，正式值以接入方业务数据和实测报告为准，不应直接套用示例数字。

估算示例（仅用于容量规划，不是当前实测）：

| 项目 | 估算 |
|---|---|
| 每日问答 | DAU × 人均请求数 |
| 单次审计记录 | 2-5 KB |
| 每日审计裸数据 | 每日请求数 × 单条记录大小 |
| 每年审计裸数据 | 每日审计裸数据 × 365 |
| 文档规模 | 按实际接入的法规、产品、研报和 FAQ 数量统计 |
| chunk 估算 | 文档数 × 每篇平均 chunk 数 |
| 1024 维 float32 向量 | 每个约 4 KB，另加索引和副本开销 |

关键结论：**查询日志会先成为最大的增长源，而不是向量库**。必须把“业务检索数据”和“审计/分析数据”分开治理。

## 2. 故障矩阵与降级

| 故障 | 用户表现 | 系统行为 |
|---|---|---|
| Redis 不可用 | 延迟略升 | 自动降级进程内 L1 + FAQ BM25；不影响回答 |
| MySQL 不可用 | 审计/会话受影响 | FAQ/记忆/审计切本地 SQLite；审计队列写 spool，恢复后重放 |
| Milvus 不可用 | 语义召回下降 | 启动时切本地向量库；运行时该分支失败后由 BM25 继续，返回降级标记 |
| LLM 超时/429 | 生成变慢 | 有界重试 + 超时 + 熔断；失败时返回通用分析或明确拒答 |
| Redis + MySQL 同时故障 | 缓存/历史失效 | 直接走 RAG + BM25，审计落本地 spool |
| 磁盘写满 | 写入失败 | 停止非关键写入、打开只读模式、健康检查降级，保护在线问答 |
| 索引重建失败 | 新文档不可见 | 保留旧索引；索引任务标记失败，不切换版本 |

## 3. 怎么避免“崩”

### 3.1 冗余

- MySQL：主从/只读副本，定期全量 + binlog 增量备份；
- Redis：Sentinel 或 Cluster，开启 AOF；
- Milvus：集群模式、副本、对象存储与 etcd 独立；
- API：无状态多副本，K8s HPA + 网关负载均衡；
- LLM：至少一个主模型 + 一个备用模型/离线降级。

### 3.2 隔离

- 检索、生成、审计、文件解析使用不同线程池/信号量，避免互相拖死；
- LLM 有并发上限，队列满时快速失败而不是无限堆积；
- 向量检索按 Collection 隔离，单库故障不影响其他资产类别；
- 读请求和写审计分离。

### 3.3 保护

- 入口限流、用户/租户配额；
- 有界队列，队列满时降级而非 OOM；
- 所有外部调用设置 timeout、重试上限和 jitter；
- 熔断器按 Redis/Milvus/LLM 分别统计错误率；
- 大文件/大图片大小限制，避免内存被打爆；
- 健康检查区分 liveness/readiness，故障副本不接流量。

### 3.4 演练

至少做四类演练：

1. Redis 停服，确认 L1/FAQ 仍可用；
2. MySQL 停服，确认审计 spool、FAQ/记忆降级；
3. Milvus 停服，确认 BM25 仍能回答并标记降级；
4. LLM 限流/超时，确认不会挂死连接和线程池。

## 4. 每次查询都存储，应该怎么做

不要让业务请求同步等待审计落库。推荐：

```text
请求完成
  → 生成 audit event（request_id, question, answer, citations, compliance, latency）
  → 有界内存队列（非阻塞）
  → 后台批量写 MySQL（每 1 秒/50 条）
  → DB 失败：写本地 JSONL spool，后台重放
```

当前代码已实现：

- `BufferedAuditStore`：异步队列 + 批量写 + spool；
- `AuditStore.purge_older_than()`：按保留天数清理；
- `resilience.audit_*` 配置；
- `request_id` 作为幂等键，避免重复写入。

生产建议再增加：

- 热表只保存 30-90 天完整审计；
- 90 天以上归档到 OSS/S3/Parquet，按日期分区；
- 分析查询走 ClickHouse/数仓，不直接扫 MySQL 大表；
- 对答案做 PII 脱敏；必要时只保存摘要和原文对象地址；
- 每日聚合指标（请求量、拒答率、合规拦截率、P95）单独存储；
- 审计写入失败率、spool 积压、队列长度纳入监控。

## 5. 数据量变大后的分区与归档

### MySQL

- `audit` 按 `created_at` 月分区；
- `messages` 按 `session_id` + 时间清理，热会话保留 5 轮，历史会话归档；
- FAQ 全量 20 万条可以保留在 MySQL，但索引和更新走增量；
- 连接池、只读副本、慢查询监控是必需项。

### Milvus

- 六个资产 Collection 独立扩容；
- 研报/新闻按时间或行业再分区，避免单个 Collection 无限增长；
- 旧产品文档标记 inactive，搜索默认过滤；
- HNSW 内存占用需要预留 30%-40% 余量；大规模时考虑 IVF/PQ，但要重测召回；
- 索引重建在低峰期滚动执行，旧 collection 作为回滚版本。

### 对象存储

- 原文 PDF/HTML、提取图片、完整审计归档放 OSS/S3；
- 文件路径和 hash 入 MySQL，数据库只存索引与元数据；
- 冷热分层：热数据 90 天，温数据 1 年，冷数据长期归档。

## 6. 三到五年的演进路线

### 第 1 阶段：单区域、模块化

- API 多副本；
- MySQL 主从 + Redis Sentinel + Milvus 集群；
- 审计异步化、按月分区；
- 文档增量索引。

### 第 2 阶段：读写分离与冷热分层

- 审计/会话归档；
- Milvus 按资产或时间分片；
- 热点答案缓存 + 请求合并；
- 引入队列（Kafka/RabbitMQ）解耦索引、审计、通知。

### 第 3 阶段：多租户与可观测

- 租户级配额、限流、隔离；
- ClickHouse/数仓做分析；
- 多区域备份与恢复演练；
- 模型路由、成本和延迟双目标调度。

## 7. 当前代码与生产缺口

已实现：

- Redis 不可用自动降级 L1/FAQ；
- MySQL 初始化失败切 SQLite；
- Milvus 初始化失败切本地向量库；
- FAQ/记忆异常不阻断回答；
- 审计异步批量写 + spool；
- 审计/会话保留策略基础方法；
- 检索分支隔离和 BM25 兜底。

仍需生产补齐：

- Kafka/消息队列、ClickHouse/数仓；
- MySQL 自动分区与对象存储归档；
- Milvus 多副本/跨可用区；
- 熔断器、连接池监控、混沌演练；
- 备份恢复自动化和 RTO/RPO 演练。

## 8. 关键结论

1. **先保证读路径可用，再保证写路径完整**：审计断了不能阻断回答。
2. **查询日志不要同步写主库**：异步、批量、spool、归档。
3. **文档数据和查询数据分开治理**：向量库只随文档增长，审计表随查询增长。
4. **每个依赖都要有降级路径**：Redis→L1，MySQL→SQLite/spool，Milvus→BM25/本地，LLM→通用分析/拒答。
5. **容量规划以 3-5 年为目标**：热数据在线、温数据可查、冷数据可归档，不能把所有历史都塞进一个 MySQL 表和一组 Milvus Collection。
